# Локальный Python-пайплайн: пакетный прототип

```text
DICOM → безопасное чтение пикселей → модель spine / hip / unknown
                                     ├─ unknown или конфликт с метаданными → ручной выбор области
                                     ├─ spine → OpenCV-ось + модель артефактов
                                     │           + модель укладки → результат для проверки
                                     └─ hip → бинарная модель качества 0/1
                                               + отдельный сигнал укладки
```

Ядро принимает один DICOM и возвращает JSON; пакетный слой принимает ZIP и
возвращает CSV. Модели загружаются один раз
при создании `DxaPipeline`, исходный файл не изменяется. Нет вывода
«клинически корректно»: ось экспериментальна, артефакт и укладка — сигналы
для проверки. Бинарная модель бедра выдаёт предварительный 0/1; отдельный
скор укладки помогает сортировать очередь. Сторону бедра из
`PatientOrientation` не выводим.

## Файлы весов

Пять файлов весов лежат в папке
проекта `models/`. Она хранится в Git LFS и копируется в Docker-образ.
После клонирования проекта выполните `git lfs pull`:

- `anatomy_spine_hip_unknown_efficientnet_b0.pt` — три области: `spine`, `hip`, `unknown`;
  вход 224×224 с сохранением пропорций.
- `spine_artifact_densenet121.pt` — DenseNet121 и голова артефактов.
- `spine_positioning_efficientnet_b0.pt` — EfficientNet-B0 и голова ошибки укладки.
- `hip_positioning_densenet121_candidate.pt` — замороженная DenseNet121 и
  обученная голова для приоритета проверки укладки бедра.
- `hip_binary_candidate.pt` — замороженная DenseNet121 и голова для
  предварительной итоговой оценки качества бедра 0/1.

Имена и пути централизованы в `dxa_ml/model_paths.py`. Четыре файла скопированы
из `Downloads` без удаления оригиналов; бинарная модель бедра обучена локально. Старый
`spine_axis_positioning_candidates.pt` не является выбранной моделью укладки.
Загружайте только собственные проверенные checkpoint-файлы: веса PyTorch
являются внешними входными данными.

## Локальный запуск

Из корня проекта, после установки `requirements-pipeline.txt` и совместимой
пары PyTorch/torchvision, достаточно указать входной DICOM:

```powershell
python scripts/run_inference.py C:\path\to\image.dcm
```

Если пользователь подтвердил область после `unknown` или конфликта модели и
метаданных, добавьте `--confirmed-anatomy spine` либо `hip` и запустите снова.
Подтверждение сохраняется в ответе как отдельный источник, а не выдаётся за
предсказание модели.

JSON содержит `image_key`, оценки маршрутизатора, технические подсказки
метаданных, результаты соответствующей ветки и `overall_status`.
Пациентские поля и сырые DICOM в JSON не включаются.

## Пакетный отчёт по ТЗ

`scripts/run_batch.py` принимает ZIP с `.dcm`/`.dicom` и сохраняет CSV: одна
строка на файл, включая повреждённые. Обязательные колонки из ТЗ:
`path_to_study`, `study_uid`, `image_uid`, `anatomical_region`,
`quality_class`, `violation_type`, `processing_status`,
`time_of_processing`. Дополнительные: `review_required`, `decision_status`,
`error_code`, `hip_positioning_score`, `hip_positioning_review_flag`,
`hip_incorrect_probability`, `hip_quality_threshold`.
`path_to_study` сейчас содержит путь файла **внутри ZIP**.

Для позвоночника `quality_class` — лишь **предварительный** 0/1 по сигналам
оси, артефакта и укладки. Даже `0` требует подтверждения человеком:
эксперименты не доказали клиническую надёжность. Порог модели укладки
отобран на малом наборе с тремя положительными случаями и служит приоритетом
проверки. `violation_type` перечисляет предполагаемые нарушения через `;`.
`Success` значит, что вычисление выполнено, **не** что снимок принят
специалистом. Для бедра `quality_class` заполняет бинарная модель, а при
ошибке тип остаётся общим: `hip_quality_unspecified`. Отдельный балл укладки
тоже включён в CSV. Сервер требует все пять checkpoint-файлов.
`unknown` и конфликт с метаданными тоже дают `Failure` до ручного выбора
области. Исходный DICOM не изменяется.

```powershell
python scripts/run_batch.py C:\path\to\studies.zip `
  --output C:\path\to\dxa_report.csv
```

Архив ограничен 512 МБ в сжатом виде, 2 ГБ после распаковки, 5000 файлами,
256 МБ на DICOM. Пути ZIP проверяются, вложенные ZIP и ссылки запрещены.
Обработка сейчас последовательная: это удерживает память и не запускает
несколько тяжёлых инференсов на одном устройстве. Распараллеливание следует
включать только после замера скорости на целевом компьютере.

## Локальный сервер и контейнер

`dxa_ml/api.py` предоставляет `POST /predict/single` (DICOM на входе,
JSON-строка таблицы на выходе), `POST /predict/batch` (ZIP на входе, CSV на
выходе) и `GET /health`. Оба POST принимают multipart-поле `file`.
Модели загружаются при старте, одновременно обрабатывается один запрос.
Сервер сам не хранит загруженные исследования. Локальный запуск берёт веса
из `models/`; для другой папки можно задать `DXA_MODEL_DIR`:

```powershell
python -m uvicorn dxa_ml.api:app --host 127.0.0.1 --port 8000 --workers 1
```

Docker на Windows: `.\scripts\run_container.ps1` из PowerShell.
На Linux/UNIX: `sh scripts/run_container.sh`. Оба скрипта собирают образ
вместе с пятью весами из `models/`. Они должны иметь имена из раздела выше;
после клонирования через Git LFS выполните `git lfs pull`.
Контейнер публикует порт **только на 127.0.0.1**. Не публикуйте API в сеть
больницы/интернет без авторизации, TLS, ограничения запросов, аудита и
согласованной политики для медицинских данных. Docker-сборка на текущем
Windows-окружении не проверена: Docker здесь не установлен. Локальные
HTTP-тесты пройдены.

## Что ещё не готово

Это технический прототип, не готовое полное решение ТЗ: раздельная причина
ошибки бедра (укладка или ROI), интерфейс ручной проверки/коррекции,
сохранение подтверждений и итоговый `.xlsx` не подключены. Бинарный ответ
бедра есть, но независимая проверка качества ещё необходима.
`DxaPipeline.predict_bytes` остаётся
общим Python-ядром для CLI и API.
